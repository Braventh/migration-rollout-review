# Mission 5 — Rollout Desk product validation

**Decision input for Mission 7: C — keep it as a useful open-source tool, but don't pursue commercialization on current evidence.** Moderate confidence in this direction; low confidence in the size of the remaining gap, willingness to switch, and willingness to pay. The narrow opportunity is a **human mixed-version rollout review that complements a linter**, not another SQL safety gate or migration runner. If a comparative trial shows repeat voluntary use, revisit **B** (position it as a companion, not a replacement). This is desk research; no interviews, recruitment, surveys, product benchmarks, or paid-product trials were conducted.

## What Rollout Desk actually does

**Verified at** [`6f348d5`](https://github.com/Braventh/migration-rollout-review/tree/6f348d595118c97f716d0bdb7abd4055532558b0) on 2026-11-23. Sources: [README](https://github.com/Braventh/migration-rollout-review/blob/6f348d595118c97f716d0bdb7abd4055532558b0/README.md), [engine](https://github.com/Braventh/migration-rollout-review/blob/6f348d595118c97f716d0bdb7abd4055532558b0/review.mjs), [architecture](https://github.com/Braventh/migration-rollout-review/blob/6f348d595118c97f716d0bdb7abd4055532558b0/docs/ARCHITECTURE.md).

- Paste PostgreSQL SQL into a browser worksheet. A PostgreSQL WASM parser supplies an AST; deterministic rules route it to nine gate families: required values, table/column renames, destructive removal, index builds, enum compatibility, type changes, foreign keys, candidate backfills, and possible table splits. Examples include DROP/TRUNCATE/unbounded DELETE, UPDATE and some INSERT…SELECT or data-writing CTE patterns, and a narrow create/copy/remove split heuristic. The engine also raises selected explicit-transaction/concurrent-DDL, enum-use, partition, search-path, and unsupported-statement notices. Procedural SQL and many other changes still need manual review. This is neither general migration lint coverage nor an inferred dependency graph.
- It can generate a bounded **read-only metadata query** for up to 12 relations. The user runs it in their own approved PostgreSQL session and pastes JSON; the app never connects to Postgres or runs migration SQL. Metadata includes relation kind/size, approximate rows, indexes and invalid/not-ready indexes, visible long transactions, primary/replica role, and standby last-replay age. No application rows are selected. Evidence is optional, stale snapshots are flagged, unqualified names may be assumed to be in `public`, and ambiguous paths can omit targets. Estimates and role-limited visibility are not runtime/locking forecasts; partition-parent figures don't sum children, and replay age is **not** replication lag.
- The user supplies actors, workers and old versions, deploy order/runner/flags, recovery builds and retirement window, owner/evidence/pause thresholds. Gates give a proposed sequence, what to verify and when to pause; each can record a human decision. The revision-checked SQLite library can reopen reviews and export Markdown including SQL and notes for manual attachment to a PR. Missing facts remain unanswered/unknown; a saved draft is **not approval**, and there is no automatic code/reference discovery, PR status gate, deploy execution, migration rehearsal, or rollback orchestration.
- Local mode: Node 24 and a loopback server, SQLite on the workstation, no account or paid service required to try the example, no app-layer auth. Hosted mode: private Devin App behind a sign-in proxy, **one organization-shared library**; anyone with access can read and update its records. Workspace mode changes copy, not per-user authorization; do not expose the server directly. Metadata and raw SQL/notes may still be sensitive, including in Markdown exports. No explicit license file was found in this checkout; option C requires owner confirmation/selection of a license before calling the repo open source.

## Answers to the decision questions

**Who already solves it, and what is free? (Verified capabilities.)** For detecting dangerous SQL, start with Squawk; Ruby/Django teams can put guardrails into the migration runtime itself. For measured lock acquisition and representative data, Eugene and self-managed DBLab address parts of rehearsal. pgroll/Reshape implement certain compatible schema transitions rather than reviewing someone else's migration. MergeBrake is already doing part of mixed-version compatibility review statically at the PR; pgschema handles review-to-apply integrity. Bytebase already offers no-fee SQL review within its Community limits. A PR template with staging and a linter can cover the coordination layer without any new app. CI does not have to be a paid capability (e.g., pgfence and MergeBrake actions on the team's existing runner), and the presence of commercial Atlas/Bytebase/Liquibase/Flyway use cases doesn't demonstrate demand for this narrower worksheet.

**Are existing workflows adequate? (Inference.)** Often yes for common DDL or disciplined teams with framework conventions, reviewers, telemetry and rehearsals. For destructive or cross-service multi-release work, reviewing each component is feasible but getting the *right evidence and explicit decisions into one review* can still be inconsistent. GitLab shows process feasibility, not how typical teams behave; repository interest and product claims do not establish adequacy for all teams. There is no measured time savings, missed-risk reduction, or retention here.

**Actual differentiation and meaningful gap? (Verified workflow, inferred value.)** The distinct combination is **migration-specific, optional read-only environmental metadata + prompts for old app/worker versions and recovery + human decisions in an exportable PR artifact, without replacing the runner or storing credentials**. “We check compatibility,” “we have a rollout plan,” “we export reports,” and “we run locally” are not unique by themselves. For example, adding an enum value may be accepted by Postgres while eligible rollback binaries or webhooks still reject that value after the first write: Rollout Desk prompts reviewers to separate DB acceptance, consumer readiness and first emission, and record the evidence/pause decision. It does **not** discover those consumers or test them. Similarly, a flag cannot turn an already persisted value back into a representable one. These are useful prompts; they could be replicated with a template. The gap is plausible in review consistency and collecting just enough evidence across heterogeneous teams; neither unmet demand nor defensibility is shown.

**Why pick it over the current workflow? (Hypothesis.)** Best initial candidate: Postgres maintainers making occasional cross-service, mixed-version changes with no migration platform and limited permission to share SQL or connect new tools to databases. Offer a better PR evidence artifact from the *same* SQL/linter result, without adding a CI gate or runner. A developer should pick it only if it either surfaces consequential considerations they'd miss (e.g. recovery worker, concurrent edits or measurable stop condition) or produces an equally actionable review faster than Squawk plus their own template. Installation, copy/paste, manually stitching migrations together, and copying the artifact back to the PR can erase the benefit. Routine changes and teams with a strong runbook, framework guardrails or an adopted governance platform are weak targets.

**Does local-first help? (Conditional, not unique.)** Yes for sensitive schema/context, offline or restricted environments, no account requirement, no target credentials in the app, and least-privilege capture via a separately approved client. This is stronger relative to SaaS requiring data upload/DB connectivity, weaker relative to Squawk, Eugene lint, local PR templates and self-hosted incumbents. It loses one shared source of truth for collaboration by default; the current hosted alternative trades data locality for one organization library and isn't per-user scoped. “No app rows” doesn't make object names, sizes, owner notes or export safe to disclose. Prove that users value this constraint and can run the capture; don't infer privacy requirements from a preference for free tools. Neither AI, hosted SaaS, nor subscription pricing is required for the hypothesis.

## What matters before adding features

| Priority | Capabilities and rationale |
| --- | --- |
| **Necessary to test the proposed niche** | Trustworthy parsing and clear rule limits for the chosen migration slice; visibly distinguish observed metadata, static inference, heuristics and unknowns; never imply safety from absence of findings. Preserve precise SQL identity, human sequencing, verification, pause and recovery decisions and unanswered items in a useful PR artifact. Keep capture optional, scoped, and privacy-aware, and work alongside the existing linter/runner. A user must be able to verify evidence provenance and redact what leaves the workstation. |
| **Only if trials prove workflow friction or omissions** | PR-native attach/automation, multi-file/change-set context, or importing an existing linter report; better snapshot provenance, if users actually rely on snapshots; shared review only if coordination is the bottleneck and access/audit controls are clear. Pick based on observed failures, not feature parity. |
| **Nice-to-have or wrong scope now** | Generic rule-count parity, proprietary schema runner, migration autofix/AI-generated approval, DB clones built into the product, automated deploy gates, hosted dashboards, account/billing/subscriptions, and integrations users won't use. Keep better-in-class tools for lint/execution/rehearsal. |

## Decision boundary

- **Choose C now, not A:** cheap local utility and a distinctive artifact are enough to preserve the option, not enough to fund a general-purpose competing platform. Confirm the distribution license; until then, treat it as a local research utility. **Not D yet:** the scoped worksheet merits a comparative trial before discarding it.
- **Change to B only with comparative evidence:** in Mission 6, use each participating developer's normal flow (including their linter, checklist and staging practice) versus the same safeguards **plus the worksheet**, with matched representative cases (enum rollback, rename across versions, and recoverable vs unsafe backfill). Counterbalance order where possible; evaluate review minutes, consequential correct misses/discoveries, actionable plans and whether users actually choose it again for another migration. Score against an independent answer key; don't reward warnings alone. Hold off on commercialization even if a demo looks good. If the free template baseline wins or users won't repeat the workflow, keep it small or reconsider D.
- **Limits:** source and first-party docs/release pages only; no runtime assertions or changes, no measured accuracy, no discovery interviews, no pricing validation with buyers, and no claim this inventory is exhaustive. The two earlier report attachments returned HTTP 401 and were not independently read; “demand unproven” also appears in the repo README and was supplied in the brief. Missions 1/3/6 results were not assumed. Pricing, limits, releases and stars are dated observations and may change.
